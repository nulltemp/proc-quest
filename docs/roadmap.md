# ロードマップ

## 目指すもの

**数時間で区切りをつけることもできれば、数百時間遊び続けることもできるゲーム。**

長く遊ぶための方向性は **ストラテジー／サンドボックス型** とする（短いランを周回するローグライト型ではない）。1つの世界の中で勢力が自分で動き続け、プレイヤーはそこに介入して世界を育てたり覆したりする。

この両立のために、次の原則を置く。

- **短く完結できる芯**：ボス撃破のような明確な目標があり、数時間で達成できる。
- **任意で深掘りできる層**：目標を達成した後も、同じ世界で遊び続けられる。長く遊ぶことを強制しない。
- **コンテンツの量よりシステムの組み合わせ**：手作りのコンテンツを積み上げるより、勢力・資源・イベントなどが相互に作用して展開が自然に生まれる仕組みを優先する（少人数でも数百時間に届かせるため）。
- **1回の判断が面白いこと**：数百時間は、同じ判断のループを何百回繰り返しても飽きないことから生まれる。

`docs/specification.md` が仕様の正本であり、本書はそこへ至るまでの検討課題と優先順位をまとめたもの。

## フェーズ1：基盤（実装済み）

長時間遊ぶこと、システムを複雑にしても調整を続けられることの前提になる基盤。

- **セーブ／ロード**（`src/game/session.ts`, `src/game/save.ts`）
  - `GameSession`（マップ・初期状態・コマンド履歴・現在状態）を JSON にシリアライズする。
  - マップは生成パラメータではなく **ノードと辺そのもの** を保存する。生成アルゴリズムを変えても古いセーブが読めるようにするため。
  - ロード時は保存された `state` を正とする。コマンド履歴はリプレイやログの復元に使うが、ターン処理のルールが変わるとリプレイ結果は一致しなくなる（その場合、Web 版はログを復元せず「再開しました」とだけ表示する）。
  - 形式は `SAVE_FORMAT_VERSION` で管理する。互換性のない変更をするときはバージョンを上げ、`parseSave` に移行処理を追加する。
  - CLI：`save [ファイル]` コマンドと `--load=<ファイル>` オプション。
  - Web：毎ターン localStorage に自動保存し、スタート画面の「続きから」で再開できる。セーブファイルのダウンロードと読み込みにも対応。
- **テスト環境**（`test/`, `npm test`）
  - 外部依存を追加せず、Node 組み込みの `node:test` を使う。
  - マップの決定性と連結性、ターン処理、セーブの往復とリプレイの一致、シミュレーションの決定性を検証している。
- **シミュレーションボット**（`src/sim/`, `scripts/simulate.ts`, `npm run sim`）
  - ボットの方針（`Policy`）に大量のゲームを自動で遊ばせ、勝率やクリアまでのターン数を集計する。
  - 現在の方針：`random`（無作為に行動）と `greedy`（強化剤を即使用、勝てる見込みが立てばボスへ向かう、それ以外は近くの宝箱を取りに行くか休息する）。
  - 新しいシステムを入れるたびに数値を測り、バランスを議論するための土台にする。

### 基盤が明らかにした最初の課題

`npm run sim` によると、現状は **`greedy` ボットの勝率が 100%**（20ノードで中央値12ターン、50ノードで25ターン）。原因ははっきりしていて、「休息」の期待値（戦力 +7.5、消耗 -1）が敵の成長（+1/ターン）を常に上回るため、休息し続ければ必ず勝ててしまう。フェーズ2で資源と勢力のモデルを作り直すとき、**「待てば必ず有利になる」状態をなくすこと**を最初の検証項目にする。

## フェーズ2：勢力システムの本格化（次に取り組む）

仕様にある「1ターンごとに全体の勢力を更新する」を、本物の勢力シミュレーションにする。ストラテジー／サンドボックス型としての遊びの中心になる部分。

検討課題：

- **ノードの支配**：各ノードに支配勢力を持たせ、支配しているノード数や種類が勢力の収入になる。
- **複数の自律勢力**：プレイヤー対敵1つではなく、3つ以上の勢力が独自の方針（拡張型、防衛型、交易型など）でグラフ上を動き、互いにも争う。
  - 勢力の AI は `src/sim` の `Policy` と同じ「状態からコマンドを選ぶ関数」として作れば、ボットとコードを共有できる。
- **資源の多次元化**：単一の `power` を、兵力・資金・士気などに分ける。何かを得ると何かを失うトレードオフを作る。
- **ターン更新の再設計**：「消耗 −1 / 敵成長 +1」という固定値を、支配地からの収入、維持費、勢力間の戦闘の結果として決まるようにする。
- **情報の不確実性**：未探索ノードの中身や他勢力の戦力が見えない「霧」、偵察コマンド。
- **外交**：同盟、停戦、従属など（フェーズ2の後半、または独立したテーマとして）。

成功の目安：シミュレーションで「何もしない」「休息し続ける」が最適にならない。同じシードでも、選んだ方針によって世界の展開が大きく変わる。

## フェーズ3：短い目標と、その後も続く世界

- **区切りとなる目標を決める**：数時間で達成できる勝利条件（ボス撃破、首都制圧など）を、シミュレーションで所要時間を測りながら調整する。
- **クリア後も続行できる**：目標を達成しても世界は終わらず、残った勢力との争い、新しい脅威、世界イベントが続く（サンドボックス型の中心）。
- **プレイヤーが選べる難易度とシナリオ**：開始条件（弱小勢力から始める、など）や世界のルール修飾（「全勢力の成長が速い」など）を選べるようにする。

## フェーズ4：組み合わせで広がるコンテンツ

- **データ駆動化**：アイテム、イベント、勢力の特性、ノードの種類を、TS のコードではなく定義データとして追加できるようにする。
- **連鎖するイベント**：あるイベントの結果が、後のノードや他勢力の振る舞いに影響する。
- **シナジー**：アイテム、勢力の特性、地形の組み合わせで戦略が変わる。
- **地域・バイオーム**：マップの領域ごとに性質を変える。

## フェーズ5：長期の世界

- **マップの階層化**：世界グラフ（地域同士のつながり）→ 地域グラフ（今のマップ）という2段構造。数百ノード以上の世界を扱えるようにする。
- **世代・時代の進行**：長期プレイで世界が変化していく（勢力の興亡、技術、時代など）。
- **プレイ記録の共有**：シード、セーブ、リプレイの共有（フェーズ1のコマンド履歴がその土台になる）。
- **性能**：大きな世界と長いセーブに耐えるよう、ターン処理とセーブサイズを見直す（例：コマンド履歴の圧縮、定期的なスナップショット）。

## 横断的な検討事項

- **バランス調整の運用**：仕組みを変えたら `npm run sim` の結果を記録し、意図しない最適戦略が生まれていないか確認する。勢力 AI が入ったら、AI 同士だけで世界を回すシミュレーションも追加する。
- **セーブ互換性**：フェーズ2以降は `GameState` の形が大きく変わるので、`SAVE_FORMAT_VERSION` の更新と移行処理（または古いセーブを読めないことの明示）が必要になる。
- **UI**：勢力や資源が増えると、テキストのステータス表示では足りなくなる。マップ上での支配状況の表示、勢力一覧、ターンごとの変化の要約などが必要になる。
