# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

proc-quest has procedural 2D graph map generation plus a first playable turn/game loop, written in TypeScript (ESM).

- Language/build: TypeScript, compiled with `tsc` per `tsconfig.json` (`module`/`moduleResolution`: `NodeNext`, `target`: `ES2022`, `strict`: true). `package.json` has `"type": "module"`, so relative imports use explicit `.js` extensions even in `.ts` source (Node ESM requirement).
- Commands: `npm install` (installs `typescript`, `@types/node`, `vite` devDependencies), `npm run build` (compiles `index.ts` and `src/**/*.ts` into `dist/`, mirrored under `dist/src/...`), `npm start` or `node dist/index.js [seed]` (prints the generated map, then starts an interactive turn loop in the terminal — type a node id to move, `quit` to exit; passing a seed reproduces the same map *and* game RNG chain deterministically). `npm run dev`/`build:web`/`preview` run the separate Vite-based browser app in `web/`, which is now also a playable client for `src/game` (click a map node to move; a status/log panel and win/lose banner reflect `GameState`), not just a map viewer.
- No test runner is configured yet — `npm test` is still the default `npm init` stub.
- No git repository is initialized. `.gitignore` exists (ignoring `node_modules/` and `dist/`) for whenever one is.
- Source layout:
  - `index.ts` — thin CLI entry point: parses an optional seed arg and an optional `--lang=<locale>` flag (falling back to the `PROC_QUEST_LANG` env var, then `en`) via `resolveLocale`, calls into `src/map` and `src/game`, prints the map, then runs the interactive per-turn prompt/response loop via `node:readline/promises`. The only file that touches `console.log`/`process.argv`/stdin.
  - `src/i18n/` — the localization module, imported by both `src/map` and `src/game` render code (and by `web/`): `locale.ts` defines `SUPPORTED_LOCALES` (`en`/`ja`), `Locale`, `DEFAULT_LOCALE`, and `resolveLocale(input)` (normalizes an arbitrary BCP-47-ish tag like `ja-JP` down to a supported `Locale`, defaulting to `en`). `messages.ts` declares the `Messages` interface (node-type/effect-type/item-type label maps, plus `map`/`game`/`cli`/`web` namespaces of strings and parameterized formatter functions). `en.ts`/`ja.ts` each implement `Messages` in full. `index.ts` barrel-exports all of the above plus `getMessages(locale): Messages`. Every user-facing formatter in `src/map/renderMap.ts`, `src/game/renderGame.ts`, and `web/render.ts`/`web/main.ts` takes an optional trailing `locale: Locale = DEFAULT_LOCALE` param and looks up strings through `getMessages(locale)` rather than hardcoding English. Adding a new `NodeType`/`ActiveEffectType`/`ItemType` or a new user-facing string requires adding it to the `Messages` interface and both `en.ts`/`ja.ts` (TypeScript's structural typing on `Messages` catches a missing key in either file).
  - `src/map/generateMap.ts` — core algorithm: random point sampling (rejection sampling for min spacing) → minimum spanning tree (Prim's) for guaranteed connectivity → k-nearest-neighbor proximity edges for an organic graph → farthest-pair BFS heuristic to place start/boss nodes → weighted node-type assignment. Exports `generateMap()`, a pure function of `(options)`, plus the `MapNode`/`MapEdge`/`MapConfig`/`GeneratedMap` types.
  - `src/map/rng.ts` — seeded PRNG (mulberry32, inlined since no external deps are used) so a given seed always reproduces the same map.
  - `src/map/nodeTypes.ts` — shared `NodeType` union (`start`/`boss`/`battle`/`event`/`normal`/`treasure`) and `NODE_TYPES`/`DEFAULT_TYPE_WEIGHTS` constants, reused by `src/game`. `DEFAULT_TYPE_WEIGHTS` covers `battle` (0.35), `event` (0.2), `normal` (0.3), `treasure` (0.15) — `start`/`boss` stay placed deterministically, not through the weighted pool.
  - `src/map/renderMap.ts` — pure string formatters (`formatMapAsText(map, locale?)`, `formatMapAsAscii`); no I/O, reusable outside the CLI. `formatMapAsText` renders node-type labels and headers through `src/i18n`; `formatMapAsAscii`'s single-character markers are language-neutral and untranslated.
  - `src/map/index.ts` — barrel re-exporting the public API of `src/map`; other modules should import through this rather than reaching into individual files.
  - `src/game/types.ts` — `GameState`/`FactionState`/`GameCommand`/`TurnEvent` types. `FactionState` also carries `activeEffects: ActiveEffect[]` (currently only `ActiveEffectType = 'shield'`, with a `charges` counter) for persistent-beyond-one-turn item effects; both `player` and `enemy` have the field (only `player` is ever populated today). `ItemType` (`'powerTonic' | 'guardianWard'`) lives here too, to avoid a circular import with `items.ts`. `TurnEvent` includes `itemAcquired`/`itemEffectTriggered` variants alongside the movement/combat/attrition ones.
  - `src/game/constants.ts` — all tunable numbers (starting power, attrition/turn, battle damage range, boss counter damage, event power range, power-tonic range, guardian-ward charge count) and `FACTION_IDS`; every number here is a placeholder default, not a spec-derived value (the design spec doesn't define any of this yet — see below).
  - `src/game/movement.ts` — `canMoveTo`/`getAdjacentNodeIds`, adjacency checks over a `GeneratedMap`'s (undirected) edges.
  - `src/game/combat.ts` — `resolveSkirmish` (rng-driven mutual damage for `battle` nodes) and `resolveBossEncounter` (deterministic power-comparison for the `boss` node, no rng). Stays unaware of items/shields — mitigation happens one layer up in `nodeEffects.ts`.
  - `src/game/items.ts` — the item catalog for `treasure` nodes: `pickItem`/`ITEM_WEIGHTS` (weighted pick, independent of `src/map`'s node-type weighting), `applyItemPickup` (grants either an instant `powerTonic` power gain or a `guardianWard` shield added to `activeEffects`), and `consumeShieldIfPresent` (mitigates one incoming damage instance if a shield is active, decrementing/removing it).
  - `src/game/nodeEffects.ts` — `resolveNodeArrival`, dispatches the above by the arrived `MapNode`'s `type`, including a `treasure` case (via `items.ts`). `battle`/`boss` damage to the player is routed through `consumeShieldIfPresent` before being applied, so an active shield can fully block one hit.
  - `src/game/state.ts` — `createInitialState(map, options)`, builds the starting `GameState` at `map.startNodeId`; both factions start with `activeEffects: []`.
  - `src/game/turn.ts` — `advanceTurn(map, state, command)`, the pure per-turn orchestrator (movement → node effects → attrition → win/lose check → next rng seed derivation). Only `move` is a supported `GameCommand` today.
  - `src/game/renderGame.ts` — pure string formatters for game state/events (`formatGameStatus(map, state, locale?)`, `formatMoveOptions(map, nodeId, locale?)`, `formatTurnEvents(events, locale?)`); no I/O, mirrors `src/map/renderMap.ts`'s role. `formatGameStatus` also lists the player's active effects (e.g. localized `Shield x1`) when any are present, and `formatTurnEvents` renders `itemAcquired`/`itemEffectTriggered`; all user-facing text (node/effect/item labels, event sentences) is looked up via `src/i18n`.
  - `src/game/index.ts` — barrel re-exporting the public API of `src/game`.
  - `web/` — a separate Vite app that both visualizes and plays the game in the browser:
    - `web/render.ts` — `renderMapToSvg(map, highlights?: MapHighlights, locale?: Locale)`, a pure SVG renderer; `MapHighlights` (`currentNodeId`/`reachableNodeIds`) adds `node-current`/`node-reachable` classes to the relevant node circles, and `locale` only affects the per-node `<title>` tooltip text (via `src/i18n`). No I/O, no click handling — mirrors `src/map/renderMap.ts`'s pure-formatter role. Per-type node radius (including `treasure`) is a table in this file, but per-type **color** is not derived from any TS table — it comes entirely from hardcoded `.node-<type>`/`.swatch.node-<type>` rules in `style.css`, so a new `NodeType` needs a manual CSS entry even though `web/main.ts`'s legend list auto-generates its (now localized) text labels from `NODE_TYPES`.
    - `web/main.ts` — the stateful driver (module-level `map`/`gameState`/`locale`), the only file with DOM/event-listener code. `regenerate()` builds a new map *and* a new `GameState` (seed input, regenerate/random buttons all start a fresh game); a delegated click listener on `#map-container` reads a clicked node's `data-id` and calls `advanceTurn` — any node is clickable, not just adjacent ones, so a non-adjacent click still consumes a turn via the engine's `blocked` event rather than being pre-validated in the UI. `formatGameStatus`/`formatMoveOptions`/`formatTurnEvents` from `src/game` are reused as-is (dumped into `white-space: pre-line` panels) rather than re-implemented for the DOM, now with `locale` passed through. `locale` is initialized from `localStorage` (`proc-quest-lang`) or else `navigator.language`, resolved via `resolveLocale`; the `#lang-select` dropdown updates it, persists it back to `localStorage`, and re-renders the static chrome labels (`applyStaticLabels`), the legend (`renderLegend`), and the current game view (`renderGame`) — it does not regenerate the map/game state.
    - `web/index.html`/`style.css` — status panel, turn log (accumulates every turn, unlike the CLI's scrolling terminal), a win/lose banner (`#banner.banner-won`/`.banner-lost`), and a `#lang-select` language dropdown (`en`/`ja`) in the header, alongside the pre-existing seed controls and legend. Static chrome text (title, seed label, buttons, log heading, lang label) lives in the HTML only as an English fallback for pre-JS paint; `web/main.ts` overwrites it from `src/i18n` on load and on language change.
- `docs/specification.md` is the design spec (see below). It only defines the win/lose conditions and the coarse turn-based/graph-map framing — it does **not** specify how faction power should update, what player commands should exist beyond movement, or combat mechanics. `src/game`'s current turn loop, faction model (two factions, `player`/`enemy`, single power scalar each), combat resolution, and the `treasure`-node item/shield mechanics in `src/game/items.ts` are all first-pass placeholder assumptions built to make the spec's win/lose conditions concrete and playable; treat the numbers in `src/game/constants.ts` and the mechanics in `src/game/combat.ts`/`nodeEffects.ts`/`items.ts` as provisional, not authoritative, until the spec is fleshed out further. Note `docs/specification.md` lists "items" only as an example of a *future command* it explicitly leaves undecided — the current `treasure` node sidesteps that by resolving automatically on arrival (like `event`), with no new `GameCommand` added; a real item-selection/use command remains open future work.

Do not assume commands or architecture beyond what's described above without checking the actual files — this section should be kept in sync as more of the game (richer commands, real combat, factions beyond player/enemy) is implemented.

## Design intent

`docs/specification.md` (written in Japanese) is the source of truth for the intended game design. Summary:

- A command-selection RPG with automatic/procedural map generation.
- The map is a 2D graph structure (nodes/points connected by edges, not a grid) — the player moves between nodes.
- At the end of every turn, all factions'/powers' strength is updated globally.
- Win condition: defeat the enemy boss.
- Lose condition: the player's own faction's power is depleted.

Refer back to `docs/specification.md` for the authoritative (Japanese) spec as the design evolves.
